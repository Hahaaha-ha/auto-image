# 部署总结参考

deploy-summary 手动整理总结和 deploy-guide 阅读总结前使用本文。总结保存上次手动整理时的经验；本次部署是否完成，以本次执行和验证为准。总结不会随其他部署操作自动更新、删除或失效。

## 软件身份与保存位置

软件标识根据用户上下文、官方项目来源及 `deploy.config.yaml` 中有来源确认的 `software_aliases` 核对。别名配置由保存和查找脚本共用，不在提示词中复制映射；不能仅凭删掉标点认定同一产品。

沿用已有阶段产物目录和总结路径。新路径用配置 `output_dir` 与 `summary_file` 代入目录使用的软件名和版本后拼接，默认是 `deploy/<现有软件目录>/<版本>/<软件>-summary.md`。别名用于识别和查找，不搬迁旧目录或另建重复总结。目录版本可以是占位或与实测版本不同；不能用目录名代替已核实版本。软件或保存路径确有歧义时先澄清，再保存。

每个软件版本保留最近一次手动总结。Markdown 文件头与正文是唯一持久记录；文件实际路径由脚本返回，不在文件头另存路径。阶段报告、安装 meta 和附件不是总结目标。旧 state、报告和无文件头的总结保持原样，不批量迁移。

## 文件头与脚本输入

从项目根调用 `python scripts/deploy_summary.py <save|find> --data <JSON文件>`；从其他工作目录调用时可用 `--root <项目根>` 明确路径根。JSON 只是输入输出，不作为新的部署记录。

| 字段 | 记录原则 |
|---|---|
| `software` | 已确认的软件标识；保存和查询都必需。 |
| `version` | 实际版本原串；save 必须给出此键，未核实写 `null`。find 可省略；目录名和 `latest` 占位不算已核实版本。 |
| `project_url` | 可选，已确认的官方项目来源。 |
| `os`、`os_version`、`architecture`、`installation_method` | 可选，已知实际值；未知留空或省略。目标环境来自用户要求、目标规格或目标机证据，不能取 agent 宿主环境代替。 |
| `updated_at` | 脚本保存时生成的带时区时间，不由调用方编造。 |

`save` 使用扁平 JSON：上述软件、版本及可选来源/环境字段，加明确 `path` 和非空 Markdown `body`。允许扩展字段，但机器/镜像关联、执行结果、材料来源和人工反馈通常写正文即可。脚本校验格式与总结路径，原子覆盖文件头和正文；不检查固定章节、上架状态、验证完整性或安装命令。失败保留旧文件，错误只影响本次保存。

成功保存返回 `{path, record}`：`path` 为项目相对实际路径，`record` 为保存后的文件头值。`find` 接收 `software`、可选目标 `version` 与环境字段，返回 `matches` 和 `warnings`；每项匹配含实际 `path`、`record`、`version_match` 及 `environment` 关系和差异。无结果时 `matches` 为空。错误由 stderr 返回具体 `error`，退出码非零。

## 阅读与适配

脚本提供查找线索，agent 阅读要采用的正文与必要附件，结合目标版本官方资料判断内容。优先读同版本；纯数字且段数一致的版本可按数值比较，较低版本由近到远列出。标签前缀、预发布、发行版后缀和无法可靠比较的版本保留原串并注明，不能仅因版本首段相同就推断兼容。

环境字段展示匹配、差异和未知，不因缺失或不同排除同产品材料。可参考多份总结；高版本、跨大版本或环境差异大的材料也可提供线索，但下载源、版本参数、配置与依赖应结合目标版本资料确认。采用后在本次指南中简述参考路径及调整。

未上架、失败或缺项的总结仍可能有用。区分已执行并验证的步骤、失败尝试、用户建议与未知信息；文件存在不证明当前机器已安装或本次验证通过。旧总结无文件头、头部损坏或不可读时，脚本提示具体路径；仅凭目录推测的身份与版本保持未确认，阅读后再判断，不能伪装成记录值。

没有匹配、内容过时/冲突/不适用、脚本运行失败或部分文件无法解析时，使用已有文件工具查找阅读，或直接继续官方资料调查。总结查找不是部署门禁，也不规定新的修复路线。
