# 部署总结参考

deploy 编排、四个部署阶段和 deploy-summary 在确定软件名称、产物路径或使用总结前读取本文。总结保存上次手动整理时的经验；本次部署是否完成，以本次执行和验证为准。总结不会随其他部署操作自动更新、删除或失效。

## 软件身份与保存位置

guide 根据输入资料及必要的官方调查确认具体项目或组件的 `project_url`。名称与来源的规范化由 `scripts/deploy_paths.py` 统一完成，保存和查找总结共用此规则，无需维护软件别名表。GitHub 根仓库默认取仓库名的小写形式，保留已有连字符；无仓库或仓库名不能代表具体产品时，使用已确认的官方产品名，必要时传 `canonical_name`。通用同名仓库、monorepo 内的不同产品要保留能够区分它们的完整来源，不能仅凭删标点、仓库最后一段或相同仓库根认定同一产品。脚本只解析已确认的输入，不联网核实来源。

新版本的目录与所有文件名前缀使用同一个规范 `software`。用户明确指定的输出路径、本次续作路径与已确认同版本的现有文件优先保留；其他版本的历史别名目录用于查找经验，不作为新版本命名依据。多处同版本路径或来源冲突时，依据本次明确上下文定位；仍有歧义才澄清，不按最近修改时间选择。目录版本可以是占位或与实测版本不同，不能代替已核实版本。

### 解析完整产物路径

guide 在确认官方项目和目标版本后、写指南前调用：

```bash
python scripts/deploy_paths.py resolve --data <路径输入JSON文件>
```

从其他工作目录调用时传 `--root <项目根>`。JSON 输入如下：

| 字段 | 含义 |
|---|---|
| `software` | 必需，用户原始软件名或已有明确软件名。 |
| `version` | 目标版本字符串；未知传 `null`，目录使用配置 `unknown_version`，返回值仍为 `null`。 |
| `project_url` | 已确认具体官方项目或组件的来源；未知可为 `null`。 |
| `canonical_name` | 可选，仅用于已核实的官方产品/组件名不同于默认仓库名等情况。 |
| `output_dir` | 可选，用户明确指定的版本目录或本次续作目录。 |
| `files` | 可选，按配置的 `*_file` 键传本次已知完整路径，例如 `install_file`；这些文件须位于同一版本目录。 |

返回 `software`、`project_url`、`version`、`output_dir` 和 `files`；输入指定 `canonical_name` 时也返回该字段。`files` 按配置的 `*_file` 键给出所有阶段及总结的完整项目相对路径；阶段文档中的这些键均指 `files` 对应值，直接用于读取或写入，转换为绝对路径时只加项目根。解析器只读、不创建文件；各阶段不再单独替换名称或拼接目录。

后续阶段优先沿用 guide 返回的完整路径。独立调用或续作缺少路径时，读取已确认的本次指南/报告，按上述输入将已有文件放入 `files` 再解析。总结沿用现有 `summary_file` 路径；需要确定新总结位置时同样解析。来源未知仍可使用精确名称和明确路径，不能为补字段虚构来源。输入、配置或路径冲突导致解析失败时，说明尚不能确定统一路径，修正已知信息后重试；未成功解析前不自行猜目录写产物。

每个软件版本保留最近一次手动总结。Markdown 文件头与正文是唯一持久记录；文件实际路径由脚本返回，不在文件头另存路径。阶段报告、安装 meta 和附件不是总结目标。旧 state、报告和无文件头的总结保持原样，不批量迁移。

## 文件头与脚本输入

从项目根调用 `python scripts/deploy_summary.py <save|find> --data <JSON文件>`；从其他工作目录调用时可用 `--root <项目根>` 明确路径根。JSON 只是输入输出，不作为新的部署记录。

| 字段 | 记录原则 |
|---|---|
| `software` | 软件输入名，保存和查询都必需；结合已确认来源按共享规则规范化，新保存文件头写规范名。 |
| `version` | save 记录实际版本原串，必须给出此键，未核实写 `null`；find 传目标安装版本，未知可省略。目录名和 `latest` 占位不算已核实版本。 |
| `project_url` | 可选，已确认的具体官方项目或组件来源，用于同源匹配；缺失时仅按精确软件名匹配。 |
| `canonical_name` | 可选，与路径解析使用同一个已确认覆盖值。 |
| `os`、`os_version`、`architecture`、`installation_method` | 可选，已知实际值；未知留空或省略。目标环境来自用户要求、目标规格或目标机证据，不能取 agent 宿主环境代替。 |
| `updated_at` | 脚本保存时生成的带时区时间，不由调用方编造。 |

`save` 使用扁平 JSON：上述软件、版本及可选来源/环境字段，加明确 `path` 和非空 Markdown `body`。允许扩展字段，但机器/镜像关联、执行结果、材料来源和人工反馈通常写正文即可。脚本校验格式与总结路径，原子覆盖文件头和正文；不检查固定章节、上架状态、验证完整性或安装命令。失败保留旧文件，错误只影响本次保存。

成功保存返回 `{path, record}`：`path` 为项目相对实际路径，`record` 为保存后的文件头值。`find` 接收 `software`、已知 `project_url` / `canonical_name`、可选目标 `version` 与环境字段，返回 `matches` 和 `warnings`；每项匹配含实际 `path`、`record`、`version_match` 及 `environment` 关系和差异。同源旧记录即使软件名不同也可找到，读取不会改写旧文件；明确不同来源不能仅因名字相同合并。缺来源且名字也不同的旧记录只可经实际阅读确认，不能猜成已确认匹配。无结果时 `matches` 为空。错误由 stderr 返回具体 `error`，退出码非零。

## 阅读与适配

每次生成或校正部署指南时，guide 默认查找已有总结，无需用户额外要求“参考历史”。查找只提供调查材料，是否采用由 agent 阅读后判断；用户明确要求不参考历史时按其要求处理。手动总结的触发方式不变。

### 目标版本与指定参考

目标版本是本次要安装、验证的软件版本，决定产物目录和指南中的版本参数。用户可另行指定参考版本或总结路径，例如“部署 nginx 1.26.2，基于 1.24.0 的总结”。这表示安装 1.26.2，优先阅读 1.24.0 的经验；参考版本不替代目标版本。用户只给参考版本时，目标版本仍按原流程从输入资料核实，不从参考总结继承；“基于”含义确有歧义且上下文无法消除时再澄清。

`find` 的 `version` 始终传本次已知目标版本（未知则省略），它返回同软件的全部匹配，不需要新增参考筛选字段。参考要求由编排原样传给 guide，并按以下方式选择：

- 指定参考版本：优先阅读返回项中 `record.version` 与指定版本原串一致的总结，其他材料用于补充。别名、版本标签或旧总结需结合来源核对，目录名不作为确认值。
- 指定总结路径：直接读取该文件并核对软件身份、正文中的版本与环境；若同时指定版本，两者应一致。路径不存在、内容不符或身份不能确认时如实记录。
- 未指定参考：按下节的默认顺序阅读和判断。目标版本尚未确定时，返回顺序不代表最新或最接近；核实目标版本后再比较。

指定材料缺失、不可读或不适用时，在指南及回复中说明具体原因与实际采用来源，继续利用可用材料和官方资料调查，不默默把其他版本称作用户指定参考。用户明确要求“仅依据该总结”或“找不到就停止”时保留该约束，不能满足则说明缺口。

### 默认选择与内容核对

脚本提供查找线索，agent 阅读要采用的正文与必要附件，结合目标版本官方资料判断内容。优先读同版本；纯数字且段数一致的版本可按数值比较，较低版本由近到远列出。标签前缀、预发布、发行版后缀和无法可靠比较的版本保留原串并注明，不能仅因版本首段相同就推断兼容。

环境字段展示匹配、差异和未知，不因缺失或不同排除同产品材料。可参考多份总结；高版本、跨大版本或环境差异大的材料也可提供线索，但下载源、版本参数、配置与依赖应结合目标版本资料确认。采用后在本次指南中简述参考路径及调整。

未上架、失败或缺项的总结仍可能有用。区分已执行并验证的步骤、失败尝试、用户建议与未知信息；文件存在不证明当前机器已安装或本次验证通过。旧总结无文件头、头部损坏或不可读时，脚本提示具体路径；仅凭目录推测的身份与版本保持未确认，阅读后再判断，不能伪装成记录值。

没有匹配、内容过时/冲突/不适用、脚本运行失败或部分文件无法解析时，使用已有文件工具查找阅读，或直接继续官方资料调查。总结查找不是部署门禁，也不规定新的修复路线。
